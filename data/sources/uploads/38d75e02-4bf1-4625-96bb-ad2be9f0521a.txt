RRavindra Dhadave"How can one thread handle thousands of users at the same time?" This is the question that confuses every Node.js beginner. Your computer has one brain (the CPU core). It can only do one thing at a time. Yet Node.js handles thousands of concurrent connections without breaking a sweat. The answer is the Event Loop. And once you understand it, Node.js will never feel like magic again. Let me explain what the event loop is and why Node.js needs it - without diving into confusing internal phases. What Problem Does the Event Loop Solve? The Single-Thread Limitation Node.js runs your JavaScript on one thread. One thread means one thing at a time. The problem: What happens when a line of code takes a long time? // What if this line takes 2 seconds? const data = fs.readFileSync('big-file.txt'); During those 2 seconds, your code stops. No other lines run. No other requests get handled. The Solution: Don't Wait Node.js solves this by not waiting for slow operations. Instead of stopping, Node.js says: "Go do that slow thing. I'll check back later. Meanwhile, I'll run other code." But who does the "checking back later"? That's the Event Loop. What is the Event Loop? The Event Loop is a continuous process that checks if there's any work to do and executes it. Think of it as a supervisor who constantly asks: "Is anything ready to run?" The Three Essential Parts To understand the event loop, you need to know three things: 1. Call Stack (What's Running Now) The call stack is a list of functions currently executing. 2. Task Queue (What's Waiting to Run) The task queue is a waiting area for callbacks that are ready to execute. 3. Event Loop (The Bridge) The event loop constantly checks: Is the call stack empty? If yes, take the first task from the queue and run it. How the Event Loop Works A Simple Example Let's trace through this code: console.log('1. Start'); setTimeout(() => { console.log('2. Timer finished'); }, 0); console.log('3. End'); Step-by-step execution: STEP 1: console.log('1. Start') Call Stack: \[console.log\] Output: "1. Start" Call Stack: \[\] (empty) STEP 2: setTimeout(...) Call Stack: \[setTimeout\] * setTimeout says: "I'll call this callback after 0ms" * The timer is handed off to the system Call Stack: \[\] (empty) STEP 3: console.log('3. End') Call Stack: \[console.log\] Output: "3. End" Call Stack: \[\] (empty) STEP 4: Timer completes (0ms later) * The callback moves to the Task Queue Task Queue: \[timerCallback\] STEP 5: Event Loop sees empty call stack * Takes callback from queue Call Stack: \[timerCallback\] Output: "2. Timer finished" Call Stack: \[\] (empty) Why Node.js Needs an Event Loop Without an Event Loop (Blocking) User 1: "Read file.txt" Server: "OK, reading..." (2 seconds frozen) User 2: "Read data.json" Server: "Still reading file.txt... wait" User 3: "Get my profile" Server: "Still reading... keep waiting" Server can only handle ONE thing at a time. Users 2 and 3 are blocked by User 1's file read. With Event Loop (Non-blocking) User 1: "Read file.txt" Server: "Started reading file.txt. I'll tell you when done." User 2: "Read data.json" Server: "Started reading data.json. I'll tell you when done." User 3: "Get my profile" Server: "Here's your profile (from memory, instantly)." Server starts all operations immediately. When file.txt finishes, User 1 gets their response. When data.json finishes, User 2 gets their response. NO ONE WAITS FOR ANYONE ELSE. How Async Operations Are Handled The Flow of an Async Operation Different Types of Async Operations Operation Type How Node.js Handles It File System Offloaded to thread pool (C++ threads) Network Offloaded to OS (epoll/kqueue/IOCP) Timers Managed by event loop internally Database Network operation (OS handles) Crypto Offloaded to thread pool Timers vs I/O Callbacks (High Level) Both timers (setTimeout, setInterval) and I/O operations (file reads, network requests) use the event loop. But they have different priorities. Simple Example const fs = require('fs'); setTimeout(() => { console.log('Timer finished'); }, 0); fs.readFile('file.txt', () => { console.log('File read finished'); }); console.log('Main code'); Output: text Main code Timer finished File read finished Why? Both callbacks are ready. But timers have their own phase that runs before I/O callbacks in the event loop. (Don't worry about the exact phases - just know that order isn't always guaranteed for very short timers.) What Matters for You // DON'T depend on exact order between timers and I/O setTimeout(() => console.log('A'), 0); fs.readFile('file.txt', () => console.log('B')); // Output could be A then B, or B then A // Both are valid behavior! The Event Loop's Role in Scalability Why Blocking Kills Scalability // BLOCKING - Handles 1 user at a time app.get('/data', (req, res) => { const data = fs.readFileSync('data.json'); // BLOCKS res.json(data); }); // With 1000 concurrent users: // Last user waits 1000 × file_read_time // If file read takes 50ms → Last user waits 50 seconds! Why Non-Blocking Scales // NON-BLOCKING - Handles all users concurrently app.get('/data', async (req, res) => { const data = await fs.promises.readFile('data.json'); res.json(data); }); // With 1000 concurrent users: // All users start at once // All users finish in ~50ms (file read time) // Last user waits NO EXTRA TIME The Scalability Formula Blocking Server Capacity = 1 request at a time Non-blocking Server Capacity = Thousands of concurrent requests (limited only by memory) Real numbers: Blocking server with 50ms operations: ~20 requests/second Non-blocking Node.js server: ~10,000+ concurrent connections Common Misconceptions "The event loop runs code in parallel" False. The event loop doesn't run code in parallel. It manages when code runs. Your JavaScript is still single-threaded. // This still takes 2 seconds total (not parallel) setTimeout(() => { while(true) {} // Infinite loop blocks everything! }, 0); // The event loop can't help with CPU-heavy code "Async code is faster" False. Async code isn't faster. It just doesn't block. // Reading 3 files takes the SAME total CPU time // But async doesn't block other work // Sync: 3 seconds total, other requests WAIT // Async: 3 seconds total, other requests DON'T WAIT "More threads = more performance" False for I/O work. For waiting operations, one thread with an event loop often outperforms many blocked threads. What Blocks the Event Loop? CPU-Intensive Operations (BAD) // ❌ This BLOCKS the event loop app.get('/fibonacci', (req, res) => { function fib(n) { if (n < 2) return n; return fib(n - 1) + fib(n - 2); } const result = fib(40); // Takes 1+ seconds of pure CPU res.json({ result }); }); // During that 1+ seconds, ZERO other requests are handled I/O Operations (GOOD) // ✅ This does NOT block the event loop app.get('/file', async (req, res) => { const data = await fs.promises.readFile('file.txt'); res.json({ data }); }); // During file read, other requests are handled normally Summary: The Event Loop in One Paragraph The event loop is a continuous process that: Checks if the call stack is empty Takes the next callback from the task queue Executes it Repeats forever This allows Node.js to handle thousands of concurrent connections with a single thread by never waiting. When an operation would block (like reading a file), Node.js hands it off to the system, continues running other code, and the event loop brings the callback back when it's ready. The Bottom Line The event loop is a task manager. It hands out tasks and processes completions. Node.js needs it because it's single-threaded. Without the event loop, every slow operation would freeze the entire server. The event loop enables scalability. By never waiting, Node.js can handle thousands of concurrent connections with minimal resources. Your job: Write non-blocking code. Use async versions of functions. Offload CPU work.
